# Руководство пользователя InsightFace Server

**Языки:** [English](user-guide.md) · [中文](user-guide.zh-CN.md) · [日本語](user-guide.ja.md) · [Deutsch](user-guide.de.md) · [Español](user-guide.es.md) · [Français](user-guide.fr.md) · Русский · [Português](user-guide.pt.md) · [한국어](user-guide.ko.md)

Это пошаговое руководство ведёт нового пользователя от пустого каталога до первого успешного поиска. Те же операции доступны через Web UI, `/v1` и Python SDK. Все HTTP-поля и результаты приведены в [руководстве по API](api.ru.md).

Модели идентифицируются по `model_id`; отдельное поле `model_version` больше не возвращается.

Обновление Server с той же моделью распознавания и контрактом сохраняет `embedding_contract_id`, образцы и эмбеддинги существующих Collections. Смена модели — отдельная миграция; несовместимый контракт вызывает `collection_model_mismatch` при регистрации и поиске.

Для проверки живого лица см. [настройку, установку модели и результаты](#необязательный-addon-проверки-живого-лица). В разделах операций также описано её влияние.

## От нуля до первого поиска

Для CPU нужны Linux x86_64, Docker Engine и Docker Compose. Для CUDA также нужны совместимый драйвер NVIDIA и NVIDIA Container Toolkit; устанавливать CUDA, cuDNN, ORT, Python или OpenCV на хост не требуется.

Выполняйте команды из корня репозитория; файл `server/config/server.toml` должен существовать. Server и установщик моделей работают как root (`0:0`). Compose создаёт `server/.models`, если каталога нет, и единственным монтированием подключает его с записью в `/models`. Подкаталог `addons` создаётся при загрузке дополнения. Экспорт UID/GID и ручная подготовка каталогов или прав не нужны. Обычный запуск Server не загружает модели; проверка живого лица по умолчанию отключена.

```bash
docker compose -f server/deploy/compose.cpu.yml pull
docker compose -f server/deploy/compose.cpu.yml run --rm models install buffalo_l
docker compose -f server/deploy/compose.cpu.yml up -d
curl -fsS http://127.0.0.1:18097/v1/health
```

Чтобы при установке модели также настроить необязательную проверку живого лица, используйте вместо обычной команды:

```bash
docker compose -f server/deploy/compose.cpu.yml \
  run --rm models install buffalo_l --accept-license --enable-liveness
```

Запускать Server заранее не нужно. При новой установке следующий `up -d` включит проверку; если Server уже работает, выполните `docker compose -f server/deploy/compose.cpu.yml restart server`. Одна команда `up -d` не перечитывает сохранённые настройки. Для CUDA используйте `compose.cuda12.yml`.

Для GPU используйте `compose.cuda12.yml` и порт `18098`. Перед загрузкой установщик показывает лицензию; публичные модели InsightFace разрешены только для некоммерческих исследований без отдельной коммерческой лицензии.

В поставляемом Compose аутентификация по умолчанию отключена для изолированной оценки. Перед сетевым доступом задайте `INSIGHTFACE_AUTH_ENABLED=true` и длинный `INSIGHTFACE_API_KEY`. Затем проверьте Dashboard, создайте Collection, зарегистрируйте Person и выполните поиск по другому фото. Останавливайте через `docker compose ... down` без `-v`, чтобы сохранить volume.

## Необязательный addon проверки живого лица

В `server/config/server.toml` проверка живого лица по умолчанию отключена: `inference.addons` и `addons.auto_download` равны `[]`. Старые настройки без этих ключей также остаются отключёнными.

**Включение через командную строку, в том числе до первого запуска Server:**

```bash
docker compose -f server/deploy/compose.cpu.yml \
  run --rm models install buffalo_l --accept-license --enable-liveness
```

`--enable-liveness` сначала проверяет возможность обновить существующую конфигурацию. Затем устанавливает и проверяет базовый пакет, настроенные для установки дополнения и модель проверки живого лица, после чего добавляет `liveness` в `inference.addons` и `addons.auto_download`, сохраняя остальные элементы, комментарии и настройки. Проверенный кэш используется повторно, но настройка включения сохраняется и при наличии моделей в кэше. Сбой загрузки не изменяет конфигурацию; ошибка её сохранения приводит к явному сообщению и ненулевому коду завершения. Годные файлы в кэше можно использовать при повторной попытке.

Оба сервиса Compose монтируют весь существующий каталог `server/config` с записью в `/etc/insightface`, сохраняя `create_host_path: false`. Поэтому установщик атомарно обновляет конфигурацию хоста без работающего Server. Каталог и `server.toml` должны существовать.

Запускать Server заранее не нужно. При новой установке следующий `up -d` включит проверку; если Server уже работает, выполните `docker compose -f server/deploy/compose.cpu.yml restart server`. Одна команда `up -d` не перечитывает сохранённые настройки. Для CUDA используйте `compose.cuda12.yml`.

Без `--enable-liveness` команда `models install` сохраняет прежнее поведение и не записывает конфигурацию; по умолчанию проверка выключена. `models addons install liveness` только загружает и проверяет дополнение, но не включает его. Также можно включить проверку через **Система → Проверка живого лица**, как описано ниже.

В разделе **Система → Проверка живого лица** выберите **Скачать и включить после перезапуска**. После проверки SHA-256 `liveness` добавляется в оба списка; остальные элементы, комментарии и настройки сохраняются. Проверенный файл используется повторно. Для применения **перезапустите Server вручную**. Ошибки допускают повтор; неудачная загрузка не включает проверку.

Система отдельно показывает проверенную установку (`installed`), текущее выполнение (`enabled`), сохранённую настройку следующего запуска (`configured_enabled`) и необходимость перезапуска (`restart_required`). Загрузка и сохранение не меняют текущий инференс. Чтобы выключить проверку, сохраните `inference.addons=[]` и `addons.auto_download=[]` в том же файле и перезапустите вручную. Web-действие не меняет настройку регистрации; её значение по умолчанию — `liveness_on_registration=false`.

**Дополнительно: ручная настройка.** Эти параметры заменяют флаг включения или действие Web; установите модель перед перезапуском.

```toml
[inference]
addons = ["liveness"]
liveness_mode = "normal"
liveness_threshold = 0.8
liveness_compare_scope = "both"
liveness_on_registration = false

[addons]
auto_download = ["liveness"]
```

### Установка модели и запуск

`inference.addons` управляет выполнением, а `addons.auto_download` — дополнительной загрузкой при установке базового пакета. С `["liveness"]` addon устанавливается и для уже кешированного пакета. При запуске Server загрузки нет. Установщик и Server читают один файл.

```bash
docker compose -f server/deploy/compose.cpu.yml run --rm models addons install liveness
docker compose -f server/deploy/compose.cpu.yml run --rm models addons verify liveness
docker compose -f server/deploy/compose.cpu.yml up -d --force-recreate
```

Отсутствующая включённая модель останавливает запуск с `addon_model_missing`, неверная — с `addon_model_invalid`. Addon не отключается незаметно.

Обновление кода с отключённой проверкой живого лица сохраняет работоспособность
существующих Collections и эмбеддингов. Миграции базы данных сохраняют образцы
и эмбеддинги; проверка живого лица не меняет дайджест модели распознавания или
`embedding_contract_id`.

### Монтирование и права для загрузки через Web

Поставляемые файлы Compose монтируют весь `/models` с правом записи; отдельное монтирование `/models/addons` не требуется. Server и установщик используют root (`0:0`), а установка создаёт `addons` при необходимости. Весь существующий каталог `server/config` монтируется с записью в `/etc/insightface` в обоих сервисах, чтобы действие Web и `--enable-liveness` могли атомарно сохранять `server.toml`. Экспорт UID/GID, `chgrp` и `chmod` при такой настройке не нужны. Файлы или монтирования, намеренно доступные только для чтения, по-прежнему блокируют Web-управление; для собственных монтирований проверьте права.

Монтирование моделей в каждом сервисе использует `create_host_path: true`. Сервисы сохраняют стандартные capabilities Docker; `cap_drop: [ALL]` не применяется. Остальная файловая система остаётся доступной только для чтения, `no-new-privileges` сохраняется. Root может изменять файлы в монтированиях с записью; новые загрузки на хосте могут принадлежать root.

При собственной схеме используйте фактические пути; для CUDA — `compose.cuda12.yml`. Старые монтирования только для чтения работают с выключенной проверкой живого лица. Web-действие поясняет причину недоступности; можно также установить модель через CLI и вручную изменить конфигурацию. После сохранения через Web примените её командой `docker compose -f server/deploy/compose.cpu.yml restart server`. Изменение монтирования или переменных прокси требует пересоздания контейнера.

Если загрузке нужен прокси, задайте `HTTP_PROXY`, `HTTPS_PROXY` и `NO_PROXY` до создания контейнера; Compose передаёт их Server и инструменту моделей. Используйте LAN-адрес, доступный из контейнера: его `127.0.0.1` не указывает на Mac. Действие использует существующую API Key аутентификацию; без неё его может выполнить любой клиент с доступом к API. Загружается только заданная опубликованная модель проверки живого лица; произвольные URL и смена базового пакета не поддерживаются.

### Результаты проверки живого лица

| Результат | `status` | `is_live` | `live_score` |
| --- | --- | --- | --- |
| Проверка пройдена | `ok` | `true` | `[0, 1]` |
| Неживое лицо | `ok` | `false` | `[0, 1]` |
| Ввод отклонён | `input_rejected` | `null` | `null` |

Только недостаточная область исходного изображения вокруг выровненного лица приводит к `input_rejected`. Такой результат дополнительно содержит `liveness.reason` — пояснение для пользователя; у живого лица и подделки поля `reason` нет. FaceAnalysis и API всегда возвращают этот текст на английском; перевод отображается только в Web-интерфейсе. В логике программы используйте `status` и `is_live`, а не текст `reason`. В ранее сохранённых результатах `reason` может отсутствовать; в этом случае клиент может показать общее сообщение об отклонении входного изображения.

```json
{
  "status": "input_rejected",
  "is_live": null,
  "live_score": null,
  "reason": "Insufficient image area around the face for liveness detection. Move the face toward the center, step back from the camera, or use a less tightly cropped image."
}
```

`normal` распознаёт только лица, прошедшие проверку; `observe` сохраняет результат и продолжает распознавание. Без проверки поле `liveness` отсутствует. Три основных поля — `status`, `is_live` и `live_score`: положительный результат/fake имеет `status: ok`, логическое значение и оценку; отклонённый вход — `status: input_rejected` и два значения `null`.

Detect возвращает HTTP 200 и для отрицательных результатов. В режиме `normal` embeddings, сравнение и поиск возвращают HTTP 422 `liveness_fake` или `liveness_input_rejected` с `error.details.liveness`; сравнение добавляет `details.side`. Сбой инференса возвращает HTTP 503 `liveness_unavailable`. Сбои выполнения прерывают операцию и в `normal`, и в `observe`; они не преобразуются в `input_rejected`.

При создании Person и добавлении FaceSample проверка по умолчанию пропускается: `[inference].liveness_on_registration=false` не запускает модель и не добавляет `liveness` к новым образцам. При `true` и включённом addon применяется режим `normal`/`observe`; отклонённые изображения содержат `reason` и `liveness`. Проверка качества по `review_mode` и валидация внешних эмбеддингов сохраняются. `review_mode=off` и `external_trusted` не обходят включённую проверку при регистрации. Запрос не может переопределить эту настройку запуска. Ранее сохранённые результаты остаются доступны.

RTSP отличает `liveness_blocked` от `unknown` и использует счётчик `liveness_blocked_faces`. Заблокированные лица не создают события входа человека/неизвестного и сбрасывают подтверждение. При сбое инференса ранее показанные личности очищаются.

`liveness_compare_scope` выбирает `both` (по умолчанию), `source` или `target` для `/v1/compare`. Проверка пройдена при `live_score >= liveness_threshold`.

Модель хранится в `server/.models/addons/liveness.onnx` на хосте и `/models/addons/liveness.onnx` в контейнере. `addons` в `/v1/models` и `/v1/system` показывает активные дополнения.

[Полный контракт API](api.ru.md#необязательный-addon-проверки-живого-лица).

## 1. Вход и готовность

Для CPU откройте `http://СЕРВЕР:18097/`, для CUDA 12 — `http://СЕРВЕР:18098/`. Если включена аутентификация, выберите **Настроить API-ключ**, вставьте ключ оператора и примените его к вкладке. Он хранится только в памяти и удаляется после обновления или закрытия.

В разделах **Панель** или **Система** убедитесь, что сервис, база, модели и Provider готовы. CUDA должен показывать `CUDAExecutionProvider` и не переключается на CPU без ошибки.

Панель всегда показывает включённую или отключённую проверку под именем модели. Система отдельно показывает установку, текущее состояние и необходимость перезапуска.

## 2. Создание Collection

В **Коллекции** → **Новая коллекция** задайте стабильный ID, имя, cosine-порог
(`0.4` сначала), доступный профиль, ёмкость и максимум FaceSamples на человека.
Сохранение JPEG `bounding-box crop`, масштабированного до 112×112, по умолчанию
выключено; это не выровненный вход модели распознавания.

Collection фиксирует ID, digest, размерность и предобработку модели. После смены модели старая Collection видима, но регистрация и поиск отклоняются, если контракт не совпадает.

Профиль детекции при создании копирует системные значения, после чего можно менять входные размеры, пороги детекции/NMS и стратегию одного лица. `largest` выбирает по площади; `center_largest` максимизирует `площадь - 2,0 × квадрат расстояния в пикселях между центром рамки и центром изображения`. Уверенность детектора в этот балл не входит.

## 3. Регистрация Person

В **Люди** выберите Collection и **Зарегистрировать человека**. Можно указать ID, имя, внешний ID, JSON metadata и несколько JPEG, PNG, WebP или BMP.

- `off`: использует стратегию одного лица Collection; несколько лиц разрешены;
- `standard`: требует одно пригодное лицо и проверяет размер, детекцию, резкость, яркость и позу;
- `strict`: дополнительно требует, чтобы лучшая внутриклассовая similarity была выше лучшей similarity с другим человеком.

Пакет может завершиться частично и сообщает причину каждого отказа. Оригиналы не сохраняются. `external_trusted` принимает L2-нормализованный embedding; изображение всё равно нужно для детекции и качества, но вектор повторно не извлекается.

Создание Person и добавление FaceSamples по умолчанию пропускают проверку (`liveness_on_registration=false`). После включения `normal` отклоняет fake/неподходящий ввод, а `observe` сохраняет результат и продолжает. Проверка качества определяется выбранным `review_mode`. Список отказов отдельно показывает фактический `reason` и результат проверки живого лица.

## 4. Детекция, сравнение и поиск

**Детекция** показывает рамки, пять точек, score и качество; отсутствие лиц — успешный пустой список. **Сравнение** выбирает по одному лицу с системным профилем или профилем Collection и возвращает cosine `similarity`, `threshold`, `matched`. Similarity не является вероятностью.

В **Поиск** выберите Collection и изображение. Оценка человека — максимум по его FaceSamples. Результаты отсортированы по убыванию; нет совпадений — пустой список. Образец сначала фиксируется в SQLite, затем до ответа добавляется в индекс. После перезапуска индекс строится из SQLite.

Каждое проверенное лицо содержит `liveness.status`, `liveness.is_live` и `liveness.live_score`. Fake и `input_rejected` также возвращают HTTP 200 без извлечения признаков распознавания. `input_rejected` означает недостаточную область изображения вокруг лица; `liveness.reason` объясняет, как скорректировать изображение. Если `liveness` отсутствует, проверки не было.

`liveness_compare_scope` (`both`, `source`, `target`) выбирает стороны для проверки перед распознаванием. В `normal` отказ возвращает HTTP 422 `liveness_fake` / `liveness_input_rejected`, `error.details.liveness` и `error.details.side`, без сходства. `observe` продолжает сравнение и возвращает результаты у проверенных лиц.

При включённой проверке в `normal` fake/неподходящий запрос возвращает HTTP 422 `liveness_fake` / `liveness_input_rejected` и `error.details.liveness`; поиск не выполняется. Это отличается от успешного пустого списка совпадений. `observe` продолжает поиск и возвращает результат у лица запроса.

## 5. Мониторинг RTSP-камеры

В **Мониторинге камер** создайте постоянный Monitor и настройте RTSP-источник, Collection, частоту, необязательный порог и правила событий. Просмотр по умолчанию выключен; распознавание и события работают без него. При включении Web UI рисует зарегистрированных зелёным, неизвестных оранжевым по `/state` поверх сырых кадров.

Monitor работает независимо от браузера, включённые задачи восстанавливаются после перезапуска сервера. Конфигурация хранится в SQLite, реквизиты RTSP зашифрованы в `/data`, но кадры и события не сохраняются. События живут только в ограниченном буфере памяти. Декодер держит последний кадр и пропускает устаревшие вместо накопления очереди.

При включённой проверке в `normal` заблокированные лица имеют `status: liveness_blocked` и отдельный результат. Они учитываются в `liveness_blocked_faces`, а не в `unknown_faces`, и не создают события входа. `observe` продолжает распознавание. Отказ по вводу и fake отображаются раздельно.

## 6. Данные и безопасность

Сохраняйте и резервируйте `/data`, каталог моделей и конфигурацию. Поставляемое развёртывание использует root со стандартными capabilities Docker и доступным для записи `/models`; сервис может изменять смонтированные модели, конфигурацию и данные. Остальная файловая система контейнера остаётся доступной только для чтения, `no-new-privileges` сохраняется; `privileged` не требуется. Ограничьте доступ к Docker и хосту, не подключайте посторонние каталоги хоста. Перед массовыми изменениями копируйте SQLite и область face crops вместе. Ключи хранятся как hash; запуск того же volume с новым `INSIGHTFACE_API_KEY` меняет активный ключ. Не пишите изображения, embeddings и ключи в журнал.

Обозреватель схемы OpenAPI для разработчиков доступен по `/docs`; практические инструкции API находятся в этой справке. Для диагностики сообщайте `x-request-id`. `401` означает проблему ключа, `409 collection_model_mismatch` — контракта модели, `422 face_not_found` — отсутствия пригодного лица.

## 7. Модели и лицензии

Образы не содержат моделей. Обычный запуск не требует сети; одноразовый сервис
`models` устанавливает пакет в `server/.models`:

```bash
docker compose -f server/deploy/compose.cpu.yml \
  run --rm models install buffalo_l --accept-license
docker compose -f server/deploy/compose.cpu.yml \
  run --rm models verify buffalo_l
```

Поддерживаются `buffalo_l` (`det_10g.onnx` + `w600k_r50.onnx`), `buffalo_m`,
`buffalo_s`, `buffalo_sc`, `antelopev2`, `raccoon_s` и `raccoon_l`.
Установка создаёт `manifest.json` и подписанный
`MODEL.LICENSE`. Без `--accept-license` интерактивный терминал запрашивает
подтверждение перед загрузкой; в неинтерактивном режиме флаг обязателен, иначе
команда завершается без загрузки. Публичные предобученные модели InsightFace
разрешены только для некоммерческих исследований без отдельной коммерческой
лицензии.

`raccoon_s` и `raccoon_l` поддерживаются. Server устанавливает только детекцию и распознавание из каждого пакета; верификатор Raccoon не загружается. Идентификатором служит имя модели, без отдельного номера версии. Web-действие проверки живого лица не переключает базовую модель. Для другой модели распознавания нужна совместимая Collection; прежние эмбеддинги не преобразуются в признаки новой модели.

## 8. Настройки запуска и поиск

```toml
[inference]
addons = []
liveness_mode = "normal"
liveness_threshold = 0.8
liveness_compare_scope = "both"
liveness_on_registration = false

[addons]
auto_download = []
```

`server/config/server.toml` читается один раз при старте; изменения требуют
перезапуска. По умолчанию: `input_sizes=[[96,96],[512,512]]`, порог детектора
`0.50`, NMS `0.40`, `single_face_selection="largest"` и максимум 100 лиц.
SCRFD запускает каждое разрешение, переносит кандидатов в координаты оригинала
и выполняет один общий NMS. `max_concurrency="auto"` означает CPU 4 и CUDA 8.
`[web].disabled=true` оставляет только `/v1` и `/openapi.json`.

System показывает лишь доступные профили. Профиль фиксируется при создании
Collection и не выбирается в отдельном Search:

- `fp32_v1`: стандарт CPU/CUDA;
- `fp16_v1`: CUDA;
- `bf16_v1`: поддерживаемый CPU или CUDA SM80+;
- `int8_x736_v1`: рекомендуемый INT8 CPU/CUDA, накопление INT32;
- `int8_x1000_v1`: совместимость старых Collections.

Все профили просматривают каждый FaceSample и не являются ANN-индексами;
публичный score остаётся raw cosine. Значения по умолчанию:
`capacity_rows=100000`, общий предел `10000000`,
`max_faces_per_person=20`. Для 512 измерений только вектор занимает примерно
2048 байт FP32, 1024 FP16/BF16 или 512 INT8 на строку.

## 9. SDK, сборка и работа с данными

Python SDK принимает путь, bytes и file-like object и предоставляет
типизированные Detect, Compare, Collections, регистрацию, Search и Monitors.
Полный HTTP-контракт находится в [руководстве по API](api.ru.md).

Можно собирать образы прямо из полного локального каталога исходного кода,
в том числе с незакоммиченными изменениями или без каталога `.git`. Коммиты
и отправка изменений в Git не являются предварительными условиями сборки.

```bash
make -C server build-cpu
make -C server build-cuda12
```

После успешного прохождения тестов публикуйте тот же образ, который был
проверен. Если затем лишь закоммитить тот же исходный код или упорядочить
коммиты, повторная сборка не нужна. Изменение файлов, включаемых в образ,
например кода, ресурсов фронтенда или встроенной пользовательской справки,
требует новой сборки и проверки.

Для локального образа добавляйте `--pull never` к Compose. Неизменяемые теги:
`0.3.1-cpu` и `0.3.1-cuda12`; движущиеся `cpu` и `cuda12` указывают на
последнюю стабильную версию, а `latest` не публикуется. Перед обновлением
остановите запись и сделайте SQLite-safe копию `/data` вместе с crops.
Не используйте `docker compose down -v`: команда удаляет volume данных.

### Обновление до 0.3.1

0.3.1 упрощает развёртывание: Server и установщик работают как root, Compose при необходимости создаёт каталог моделей, а единый доступный для записи `/models` заменяет отдельное монтирование addons.

Начиная с 0.3.0 поддерживаются `raccoon_s`, `raccoon_l`, их манифесты, необязательная проверка живого лица, установка дополнений через Web и изображения BMP. Server использует детекцию и распознавание Raccoon; верификатор не загружается. Эти возможности и контракты ответов API не меняются в 0.3.1.

**1.** Обновите исходный код Server и файлы Compose до версии 0.3.1, сохранив
настройки `server/config/server.toml` и свои переопределения конфигурации
развёртывания. Сохраните существующий путь к моделям, имя тома `/data`,
хранилище crops, порты и настройки API Key. В собственных файлах Compose
обновите образы обоих сервисов, `server` и `models`, до `0.3.1-cpu` или
`0.3.1-cuda12` для соответствующей среды. В командах ниже используйте те же
файлы Compose, переопределения и имя проекта, что и в текущей установке.

Перед запуском обновите также собственные переопределения Compose, а не только теги: оба сервиса должны использовать `user: "0:0"`, без `cap_drop: [ALL]` и прежних настроек UID/GID или `group_add`. Для обоих сервисов используйте единственное bind-монтирование с записью в `/models` и `create_host_path: true`; удалите отдельное монтирование `/models/addons` и `x-addons-path`. Сохраните фактический путь моделей и существующие файлы, включая addons. Монтирования конфигурации сохраняют `create_host_path: false`, поэтому `server/config` и `server.toml` должны существовать. Сохраните том данных и перед изменением сделайте резервную копию данных, моделей и конфигурации. Удалите старые настройки пользователя и монтирований из собственных переопределений; замена одного образа этого не делает.

Сохраните режим только для чтения для файловой системы контейнера и `no-new-privileges`. Обоим сервисам нужен весь каталог конфигурации с записью. Замените старое монтирование единственного файла только для чтения у установщика на монтирование каталога. Стандартное развёртывание не требует рекурсивного изменения существующих прав или подготовки каталога addons.

**2.** Загрузите новые образы и пересоздайте контейнер Server. Из корня репозитория
выполните команды для своей существующей установки:

CPU:

```bash
docker compose -f server/deploy/compose.cpu.yml pull server models
docker compose -f server/deploy/compose.cpu.yml up -d --no-build --force-recreate server
curl -fsS http://127.0.0.1:18097/v1/health
```

CUDA:

```bash
docker compose -f server/deploy/compose.cuda12.yml pull server models
docker compose -f server/deploy/compose.cuda12.yml up -d --no-build --force-recreate server
curl -fsS http://127.0.0.1:18098/v1/health
```

При локальной сборке сначала соберите образы 0.3.1, а вместо загрузки
используйте `up -d --no-build --pull never --force-recreate server`.
Одной команды `docker compose restart` недостаточно для перехода на новый
образ или применения изменений монтирования.

**3.** При запуске миграции базы данных применяются автоматически. Дождитесь,
когда `/v1/health` сообщит `ready` и версию `0.3.1`, затем проверьте
ожидаемую модель и провайдер выполнения в разделе **Система**. Убедитесь,
что существующие Collections и люди на месте, и выполните поиск с известным
результатом. При сохранении той же модели и контракта эмбеддингов образцы,
эмбеддинги и идентификаторы контрактов Collections сохраняются;
повторная регистрация не нужна.

**После обновления проверка живого лица остаётся необязательной.** Поставляемая
конфигурация и старые конфигурации без ключей addon оставляют её отключённой,
поэтому само обновление не требует загрузки модели проверки живого лица.
Server никогда не загружает модели при запуске. Для включения следуйте
[инструкции настройки](#необязательный-addon-проверки-живого-лица): подготовьте
[монтирования и права для загрузки через Web](#монтирование-и-права-для-загрузки-через-web),
выберите **Система → Проверка живого лица → Скачать и включить после перезапуска**,
дождитесь успешной установки и сохранения конфигурации, затем вручную
перезапустите Server. Значения по умолчанию: `normal`, порог `0.8` и
`liveness_on_registration=false`. Модель остаётся по пути
`<models_dir>/addons/liveness.onnx`.

**Переход на Raccoon — отдельная смена модели.** Обновление Server сохраняет
текущий пакет моделей. Чтобы использовать `raccoon_s` или `raccoon_l`,
установите выбранный пакет в отдельный каталог моделей по
[инструкции установки](#7-модели-и-лицензии), затем настройте развёртывание
для его использования. Collections должны соответствовать контракту
эмбеддингов новой модели; создайте совместимые Collections и зарегистрируйте
людей заново либо выполните отдельную миграцию данных. Web UI не переключает
базовые пакеты моделей.

**Совместимость API и SDK начиная с 0.3.0:** Результаты моделей, Collections и FaceSamples
больше не содержат `model_version`; модель определяется через `model_id`,
а совместимость Collection — через `embedding_contract_id`. Обновите клиенты,
которые требуют удалённое поле, и при обновлении поставляемого Python-клиента
используйте SDK `0.3.1`. Когда проверка живого лица выполнена, `liveness`
содержит основные поля `status`, `is_live` и `live_score`, а при `input_rejected`
также `reason`; если проверка не выполнялась,
поле отсутствует. Перед включением проверки для запросов распознавания
изучите [правила результатов и ошибок](#результаты-проверки-живого-лица).

## 10. GPU, сеть и устранение неполадок

CUDA-образ содержит CUDA Runtime 12.9.1, cuDNN 9.24.0 и
`onnxruntime-gpu==1.27.0`. Turing/Ampere/Ada/Hopper требуют R535+, Blackwell и
RTX 50 — 570.26+; для новых установок рекомендуется стабильный R580+.
При старте проверяются GPU, Compute Capability, Driver, CUDA/cuDNN/ORT,
Provider, настоящие model Sessions и warm-up; скрытый переход на CPU запрещён.

При сетевой публикации завершайте HTTPS на доверенном reverse proxy,
ограничивайте CORS origins, rate, body и timeout и защищайте `/data` и backup
как биометрические данные. Не журналируйте изображения, embeddings и ключи.
В первой фазе есть один API Key без ролей — это не multi-tenant авторизация.
